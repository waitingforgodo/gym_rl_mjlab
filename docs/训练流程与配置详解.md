## 1. 文件在哪里，环境如何隔离

Ubuntu 侧运行工作空间：`/home/godot/g1-mjlab-workspace`，本文以 `~/g1-mjlab-workspace` 表示。

解释器复用 `~/mjlab-isolated-v160/.venv/bin/python`，具体路径保存在 `.runtime-path`。原环境已经能运行 GPU 仿真，当前工作空间不额外安装一套依赖，也不修改其源码。

`g1.sh` 在子进程里清理外部 Conda/Python 路径，把 Warp、CUDA、Torch、临时文件等缓存放入本空间 `.cache`，默认限制相关 CPU 库为 2 线程、CPU nice=10。每次运行都会进入正确工作目录，无须先 activate。

这属于文件与运行配置隔离，CPU、GPU、WSL 内存仍共享，不是虚拟机/显存配额隔离。启动两个训练或同时回放会竞争资源。脚本不会停止你其他目录里的任务，也不改 `.wslconfig`、驱动或系统时钟。

当前已测 GPU 是 RTX 5070 Laptop、约 8 GiB 显存，WSL Ubuntu 22.04.5 LTS、约 15 GiB 可见内存。已安装运行时使用支持这台显卡的 CUDA 12.8 版 Torch；需要确切依赖版本时运行 `00_check.sh` 的 doctor 报告。`nvidia-smi` 的 CUDA 字段表示驱动支持能力，不等于系统一定安装了相同版本的完整 CUDA Toolkit。

## 2. 一次训练的完整调用链

```text
scripts/03_resume.sh
  → g1.sh：解释器、缓存、CPU 设置
    → workspace/cli.py：解析参数、解析模型路径、获取文件锁
      → runtime.initialize：核对依赖版本、注册官方任务
      → runtime.build_configs：官方配置副本 + profile + CLI 覆盖
      → validate_resume：任务、版本、profile/动作哈希、频率兼容检查
      → 写 run_manifest.json 和 params/*.yaml
      → ManagerBasedRlEnv：创建物理场景与各个 manager
      → RslRlVecEnvWrapper：适配 PPO 的观测、动作、终止接口
      → 官方任务 runner：加载 checkpoint，执行 PPO
      → 保存模型、TensorBoard event、资源采样
      → flush 日志、关闭环境
```

训练流程不经过 Isaac Lab 的 AppLauncher 或 PhysX。gym_rl 的资料主要用于理解任务、列顺序和动作数据；物理仿真在 MuJoCo/Warp 中执行，PPO 由 RSL-RL 实现。

## 3. 当前任务要学什么

任务 ID 为 `Mjlab-Velocity-Flat-Unitree-G1`。当前快捷脚本使用 `velocity_flat_4096`；旧文中的 `velocity_flat` 是保留的原始基线 profile。

策略每次读取机器人状态及期望机体系速度，输出 29 个关节位置目标的归一化动作。目标包括跟随前后/横向速度与偏航角速度、保持平衡和合理姿态，同时减少大动作变化、关节越界、滑脚和碰撞等。

它不是按给定关节轨迹逐帧复现舞蹈。舞蹈使用 `Mjlab-Tracking-Flat-Unitree-G1`、本地动作 NPZ 与另一套命令/奖励。

## 5. 物理与控制频率

官方平地配置的物理时间步长为 `0.005 s`，即 200 Hz；`decimation=4`，每 4 个物理步更新一次策略，因此策略周期 `0.02 s`、频率 50 Hz。

一个策略动作不是持续一秒：它生成的关节目标在随后的四个物理子步中由模拟驱动跟踪。改变 decimation 或 timestep 会同时改变状态变化、奖励积分、接触行为和动作频率，不能只为提升 FPS 随意修改。

平地配置使用 MuJoCo solver iterations=10、line-search iterations=20、ccd_iterations=50；njmax=300、contact_sensor_maxmatch=64，具体仍以 env.yaml 为准。普通训练 episode 上限 20 秒；play 设置约 1e9 秒的上限，保留跌倒终止。

## 6. Actor 99 维、Critic 111 维怎么来的

你贴出的实际运行日志已经确认这组维度。

Actor 每步输入包含：

- 基座线速度：3 维，来自配置的机载速度传感器。
- 基座角速度：3 维。
- 机体系投影重力：3 维。
- 相对默认关节位置：29 维，训练时考虑编码器偏置。
- 关节速度：29 维。
- 上一次策略动作：29 维。
- 期望速度命令 `(vx, vy, wz)`：3 维。

总计 `3+3+3+29+29+29+3=99`。平地任务删除了地形高度扫描观测。

Critic 在这些状态基础上额外看到两只脚的高度、腾空时间、接触状态和接触力，共增加 12 维，得到 111 维；它还使用真实无编码器偏置的关节位置。Critic 只服务于训练的价值估计，部署策略只需要 Actor 的 99 维输入。

两个网络均为 `输入 → 512 → 256 → 128 → 输出`，隐藏层激活为 ELU，带 EmpiricalNormalization。Actor 输出 29 维，Critic 输出一个价值。推理使用确定性动作输出，训练还通过高斯分布采样进行探索，初始标准差为 1.0。

## 7. 动作如何变成机器人运动

原始策略输出为无量纲 action。若 wrapper 配置了 clip_actions，先裁剪 action，然后按动作顺序计算：

```text
processed_target = action × action_scale + action_offset
再按配置裁剪 processed target
模拟关节目标 = processed_target − encoder_bias
```

本任务使用默认关节位置作 offset。G1_ACTION_SCALE 依据每类关节的驱动力矩和刚度设置，不是所有关节固定同一个 0.25；不要直接把 29 维 action 当作弧度发送给 SDK。

官方驱动使用各关节组的刚度、阻尼和能力约束。导出清单从实际模型取 PD、默认位置和动作缩放，不在本空间手写一套旧 rl_sar 数组。PD 数组是自然关节顺序，动作数组是 action 顺序，通过名字映射到 SDK 顺序。

## 8. 一次 PPO 更新发生什么

当前官方配置每个环境收集 `num_steps_per_env=24` 个策略步。4096 环境时：

```text
一次 PPO 更新的样本数 = 4096 × 24 = 98304
每环境覆盖的仿真时间 = 24 × 0.02 = 0.48 秒
4 个 mini-batch → 每份约 24576 条样本
5 个学习 epoch → 每次 PPO 更新约进行 20 次 mini-batch 优化
```

Actor 采样动作，环境返回奖励和终止，Critic 估计价值，GAE 构造优势和回报，再用 PPO clipped objective 更新。更新次数、环境步数、物理子步数和真实时间是四种不同计数。

当前 PPO 基线的关键值：

- learning_rate=0.001，schedule=adaptive，desired_kl=0.01。
- gamma=0.99，lam=0.95。
- clip_param=0.2，use_clipped_value_loss=True，value_loss_coef=1.0。
- entropy_coef=0.01，max_grad_norm=1.0。
- num_learning_epochs=5，num_mini_batches=4。

自适应学习率会根据 KL 变化，因此日志里降到 1e-5 并不单独证明程序出错。要结合奖励、episode 长度、动作标准差和独立评估。`velocity_gym_ppo` 是另一个对比实验，仅将 entropy_coef 改为参考资料的 0.008，不能把它当作已验证更好的参数。

## 9. 奖励、随机化与课程

速度/偏航跟踪奖励分别以权重 2.0 奖励接近期望速度，upright 和姿态奖励帮助保持身体与关节姿态。负项抑制身体摇晃、角动量、关节越界、动作变化、滑脚、脚高偏差、落地冲击和自碰撞。

G1 配置中 air_time 的权重是 0，所以日志中的 air_time=0 不能直接说明机器人没有抬脚。奖励 manager 默认乘控制周期 dt，训练里记录的回合平均奖励与评估里的单步 reward 不是同一口径，不能直接比较数值大小。

训练 Actor 的部分观测加噪声；脚摩擦、编码器偏置和基座质心有随机化；训练会施加基座速度扰动。play 关闭 Actor 噪声和 push，但保留其他配置，所以当前评估也不是完整训练难度下的鲁棒性测试。

速度课程按环境公共步计数推进，不按所有并行环境的总样本数推进：

- 初期前进速度范围 `[-1,1] m/s`，偏航角速度 `[-0.5,0.5] rad/s`。
- 约 `5000×24` 个公共策略步后，扩到前进 `[-1.5,2]`、偏航 `[-0.7,0.7]`。
- 约 `10000×24` 步后，再扩大前进范围。

增加 num_envs 会增加每轮样本，不会相同比例提前跨越这些公共步门槛。resume 恢复 checkpoint 保存的 common_step_counter，是否已到某阶段以实际课程记录为准。

## 11. 当前电脑的并行实测

用户在 Ubuntu 跑过 512/1024/2048 的 100 更新短测，三档均通过；这是当时把快捷脚本设为 2048 的依据。随后 AMP 与两种 tracking 又通过 4096 容量短测，当前默认已更新，详见 [4096 并行配置与容量结果](4096并行配置与容量结果.md)。

原始 30 次短测出现过负 learning_time。固定依赖用 time.time 计算耗时，系统时间回拨可造成该异常；本空间只在当前训练进程的 runner 模块中换成 perf_counter，结束后恢复。标准库、系统时钟和依赖文件都未修改。汇总还会拒绝负值、缺项和非有限计时。

这个结论是短测吞吐选择，不等于长期热稳定性或策略质量最优。benchmark 每档从头学习，得到的模型只服务性能测试；正式训练继续使用自己的训练模型。

### 12.2 总体训练效果与终止情况：6 条

| 曲线 | 含义 | 阅读方法 |
| --- | --- | --- |
| `Train/mean_reward` | 最近 100 个已结束回合的平均累计奖励，未作折扣 | 同一奖励配置和任务难度下，整体提高通常表示学习有进展；还要结合回合长度和速度误差 |
| `Train/mean_episode_length` | 最近 100 个已结束回合的平均长度，单位为控制步 | 当前控制频率 50 Hz，1000 步约为 20 秒，接近训练回合上限；它不包含尚未结束的回合 |
| `Train/mean_reward/time` | 与 mean_reward 相同的纵轴数据，横轴改为累计采样和优化耗时 | 用于按训练耗时比较进展 |
| `Train/mean_episode_length/time` | 与 mean_episode_length 相同的纵轴数据，横轴改为累计采样和优化耗时 | 用于观察经过多少训练时间后回合变长 |
| `Episode_Termination/fell_over` | 倾倒终止事件的聚合计数；当前任务依据过大的姿态倾角判断倾倒 | 在相同并行数、采样和任务条件下比较趋势，下降通常更好 |
| `Episode_Termination/time_out` | 达到训练回合时间上限的终止事件聚合计数 | 与倾倒减少、回合变长一起看，反映更多回合运行到时间上限 |

`Episode_Termination/*` 先由环境在复位时统计，再由 runner 聚合平均，因此可能出现小数。它们**不是失败率或成功率**，也不能不加换算地跨并行数比较。要判断固定观察窗口内有多少环境没有失败，使用第 13 节评估输出的 `no_failure_fraction_over_horizon`、`per_env_failure_counts` 等直接统计。

例如，平均回合长度约 999 步对应约 19.98 秒；这说明最近完成的回合较长，但不单独证明各种速度和转向命令下都能稳定行走。

### 12.3 速度跟踪、动作与物理表现：7 条

| 曲线 | 含义 | 阅读方法 |
| --- | --- | --- |
| `Metrics/twist/error_vel_xy` | 平面速度命令与实际机体系速度之间的误差趋势 | 同一统计口径下越低越好；当前由命令模块按时间累积并缩放，不是评估 RMSE |
| `Metrics/twist/error_vel_yaw` | 偏航角速度命令与实际偏航角速度之间的误差趋势 | 同一统计口径下越低越好；同样不能直接当成评估 RMSE |
| `Episode_Metrics/mean_action_acc` | 归一化策略动作的平均绝对二阶差分 | 通常越低表示动作变化越平顺；公式为 mean(abs(a_t - 2*a_(t-1) + a_(t-2)))，没有除以时间步长平方，不是实际关节加速度 |
| `Metrics/angular_momentum_mean` | 全身角动量大小的平均值 | 观察整体转动和摆动强度，需要在相近命令速度下比较 |
| `Metrics/slip_velocity_mean` | 脚接触地面时的平均平面滑动速度，单位 m/s | 通常越低越好，结合脚底接触和回放判断滑脚 |
| `Metrics/peak_height_mean` | 落地事件对应的摆脚峰值高度，单位 m | 当前目标摆脚高度为 0.1 m，需要结合目标和回放判断，不能一味追求更高 |
| `Metrics/landing_force_mean` | 落地事件的平均接触力大小，单位 N | 用于观察冲击和落地柔顺性，比较时保持命令与步态条件一致 |

落地相关指标在没有落地事件的采样中可能记为 0，随后还会被日志聚合。因此，曲线均值不能直接解释为“每一步都只抬这么高”或“每次落地都是这个力”。

速度误差的定量验收使用评估 JSON 中的 `velocity_xy_rmse_m_per_s` 和 `yaw_rate_rmse_rad_per_s`，并保持评估时长、命令协议、种子等条件一致。

| `Episode_Reward/body_ang_vel` | 惩罚躯干横滚、俯仰方向过大的角速度 | -0.05 | 负值趋近 0 |
| `Episode_Reward/angular_momentum` | 惩罚过大的全身角动量 | -0.02 | 负值趋近 0 |
| `Episode_Reward/dof_pos_limits` | 惩罚关节位置超出软限位 | -1.0 | 负值趋近 0 |
| `Episode_Reward/action_rate_l2` | 惩罚相邻策略动作变化过大 | -0.1 | 负值趋近 0，同时保留跟踪能力 |
| `Episode_Reward/air_time` | 脚部腾空时间奖励 | 0.0 | 当前未启用，一直为 0 正常 |
| `Episode_Reward/foot_clearance` | 按脚部运动速度加权，惩罚离地高度偏离目标 | -2.0 | 负值趋近 0 |
| `Episode_Reward/foot_swing_height` | 落地时惩罚本次摆脚峰值高度偏离目标 | -0.25 | 负值趋近 0 |
| `Episode_Reward/foot_slip` | 惩罚脚接触地面时滑动 | -0.1 | 负值趋近 0 |
| `Episode_Reward/soft_landing` | 惩罚落地冲击 | -0.00001 | 负值趋近 0 |
| `Episode_Reward/self_collisions` | 惩罚机器人自身碰撞 | -1.0 | 负值趋近 0 |

这些值已包含权重和时间统计：奖励管理器累计各项加权奖励，复位时按最大回合秒数归一化，runner 再聚合。它们不是原始速度、角度、力等物理量，也不与最近 100 个已结束回合的 `Train/mean_reward` 使用完全相同的聚合口径。

不同分项的尺度和权重不同，不能只比较谁的绝对值大。惩罚项较小还可能与回合提前结束、命令难度改变有关，需要同时查看回合长度、误差和回放。

### 12.5 网络优化与探索：5 条

| 曲线 | 含义 | 阅读方法 |
| --- | --- | --- |
| `Loss/value` | Critic 的价值预测损失 | 关注是否稳定、有无突然发散；目标随策略变化，不要求持续降到 0 |
| `Loss/surrogate` | PPO 的策略优化目标 | 负值正常，不按普通监督学习预测误差解释，也不要求单调下降到 0 |
| `Loss/entropy` | 动作分布的熵，反映探索程度 | 没有固定的“越低越好”规则；结合奖励、误差和策略标准差看 |
| `Loss/learning_rate` | 当前优化器学习率 | 本配置根据 KL 自适应调整，观察其变化与优化状态，不是一味越大或越小越好 |
| `Policy/mean_std` | 策略动作分布的平均标准差 | 通常随学习逐渐收缩；过早收缩或持续很大时，结合训练效果判断探索是否合适 |

`Policy/mean_std` 描述策略分布，不是机器人关节角的标准差，也不是每一步动作变化量。

### 12.6 训练性能：3 条

| 曲线 | 含义 | 阅读方法 |
| --- | --- | --- |
| `Perf/total_fps` | 所有并行环境每秒产生的总策略步数 | 反映训练吞吐；不是网页渲染帧率，也不改变机器人的 50 Hz 控制频率 |
| `Perf/collection_time` | 每轮采样耗时，单位秒 | 用于观察环境推进和采样阶段的耗时变化 |
| `Perf/learning_time` | 每轮 PPO 更新耗时，单位秒 | 用于观察优化阶段耗时；出现负数、NaN 或 Inf 时先排查计时和运行状态 |

当前单 GPU 下，`total_fps` 约等于 `并行环境数 × 24 / (collection_time + learning_time)`。吞吐较高说明采样更新更快，不能据此判断步态质量。

### 12.7 速度课程范围：6 条

| 曲线 | 含义 | 单位 |
| --- | --- | --- |
| `Curriculum/command_vel/lin_vel_x_min` | 前后速度命令下限 | m/s |
| `Curriculum/command_vel/lin_vel_x_max` | 前后速度命令上限 | m/s |
| `Curriculum/command_vel/lin_vel_y_min` | 横向速度命令下限 | m/s |
| `Curriculum/command_vel/lin_vel_y_max` | 横向速度命令上限 | m/s |
| `Curriculum/command_vel/ang_vel_z_min` | 偏航角速度命令下限 | rad/s |
| `Curriculum/command_vel/ang_vel_z_max` | 偏航角速度命令上限 | rad/s |

这些曲线显示任务要求的命令范围，不能当作机器人实际达到的速度。当前初期范围为前后/横向速度各 `[-1, 1] m/s`、偏航角速度 `[-0.5, 0.5] rad/s`。课程范围在阶段切换前保持水平是正常现象，阶段推进规则见第 9 节。

### 12.8 推荐阅读顺序与源码位置

1. 看 `Train/mean_reward` 与 `Train/mean_episode_length`：奖励是否提高、回合是否变长。
2. 看 `Metrics/twist/error_vel_xy`、`error_vel_yaw` 与 `Episode_Termination/fell_over`：跟踪是否改善、失败是否减少。
3. 看奖励分项和物理表现：定位滑脚、冲击、摆脚高度、姿态或动作抖动问题。
4. 看 `Loss/*` 与 `Policy/mean_std`：辅助判断优化和探索状态。
5. 看 `Perf/*` 与 `Curriculum/*`：确认吞吐和任务难度是否改变。
6. 用相同协议的回放和定量评估确认改进；多项趋势一致比某一条曲线好看更有依据。

曲线可能经过平滑。先查看原始波动，再用相同平滑系数比较趋势；不同实验还应保持横轴、任务、命令难度和统计口径一致。

实现位置可用 `bash ~/g1-mjlab-workspace/g1.sh show-sources --kind velocity` 定位。RSL-RL 的 `utils/logger.py` 写入 `Train/*`、`Loss/*`、`Policy/*` 和 `Perf/*`；mjlab 的 `managers/reward_manager.py`、`termination_manager.py`、`metrics_manager.py` 负责回合统计；`tasks/velocity/mdp/velocity_command.py`、`rewards.py` 和 `curriculums.py` 负责对应误差、物理指标和课程范围。

## 13. 回放与数值评估分别看什么

```bash
bash ~/g1-mjlab-workspace/scripts/04_play.sh
bash ~/g1-mjlab-workspace/scripts/05_evaluate.sh
bash ~/g1-mjlab-workspace/scripts/06_evaluate_forward.sh
```

04 用 `http://localhost:8080` 看动作是否出现拖脚、抖动、单侧支撑异常或转向失稳。

05 使用官方 play 随机命令。平地 play 的前进速度范围是 `[-1.5,2] m/s`、偏航范围 `[-0.7,0.7] rad/s`，还有横向速度、随机航向/站立分支；这可能比初期训练范围更难。

06 只测试机体系前进 0.5 m/s、零横向、零偏航，从静止起步，关闭随机站立、航向、世界系和前进专用命令分支。它用较简单条件检验基础前进能力；通过后再看随机命令，不把这两种协议的结果混为一组。

评估会把协议写进 JSON，输出主要字段：

- failure_terminations：失败事件总数；一个环境可失败多次。
- environments_with_failures / without_failures：这次时窗中是否出现过失败的环境数。
- no_failure_fraction_over_horizon：观察时窗内从未失败的样本比例。
- per_env_failure_counts、first_failure_time_seconds：定位重复失败和首次失败时间。
- velocity_xy_rmse_m_per_s：平面误差向量范数的 RMSE，sqrt(mean(ex²+ey²))。
- yaw_rate_rmse_rad_per_s：偏航角速度 RMSE。
- completed_episode_seconds_mean：只统计已结束片段，未结束的长时间存活样本不在均值里。

当前你贴出的 model_3198 结果：16 环境各观察 60 秒，累计 960 环境秒，5 次跌倒终止；最后片段显示 12 个环境完整跑满 60 秒，4 个发生过失败。因此本时窗无失败样本比例是 75%，不能把 5/16=31.25% 当作失败环境比例。平面 RMSE=0.717 m/s、偏航 RMSE=0.394 rad/s，说明仍需改进速度跟踪，且随机命令有一定难度。

该结果里的 Episode_Reward 约 1e-8，原因是官方 play 回合上限约 1e9 秒，而该日志按最大回合秒数归一化。它不是训练奖励突然消失。新评估不再把这些复位日志快照冒充固定时长指标；用直接计数、直接采样 RMSE 和 reward_per_step_mean 判断。

`joint_angle_rmse_rad=null` 在 velocity 任务中正常，因为没有逐帧关节参考轨迹；tracking 才会计算该项。99/111/29 网络维度也是当前任务的正常输出。

## 14. 接下来怎么调

先用固定前进协议评估同一个 model_3198，再以相同协议比较新增 1000 次更新后的模型。如果固定前进明显正常、随机命令较差，重点检查高速、横移和转向覆盖；如果两者都差，再看训练奖励、课程阶段、学习率与回放动作。

当前没有足够证据要求立刻改奖励或网络。需要实验时，单独建立 profile，明确只改一个因素；保持基线模型和评估协议。编辑 profile 会改变哈希，现有 resume 会拒绝混用，应从零建立新实验。当前没有另行实现“只初始化网络、重置优化器的跨配置 warm-start”命令。

## 15. 动作模仿如何接入

`10_import_motions.sh` 从 D 盘 gym_rl 只复制两份 CSV，保留来源和哈希。转换依次处理 xyzw→wxyz、时间重采样、SDK→当前关节名顺序、CPU 正运动学、世界系线/角速度，输出 NPZ。它不执行 Isaac Lab 代码，也不加载资料中的旧策略。

`11_train_tracking.sh` 使用本地 dance_102 NPZ、官方 tracking 任务，当前脚本默认 `tracking_4096`；旧 profile 保留以兼容已有模型。`tracking_no_state_estimation_4096` 去掉 Actor 的 base_lin_vel 和 motion_anchor_pos_b，观测不同，需另起训练，不能直接切换已有模型。

动作转换成功只证明数据格式和运动学链路可用；关节极限、接触、穿地和动作动态可行性仍需跟踪评估。当前已单独验证两种 tracking 的 4096 环境短时容量，结果见 [4096 并行配置与容量结果](4096并行配置与容量结果.md)。

## 16. 导出、仿真部署和真机配置

```bash
bash ~/g1-mjlab-workspace/scripts/08_export.sh
bash ~/g1-mjlab-workspace/scripts/09_deploy_sim.sh --bundle /实际导出目录
```

导出包括 policy_jit.pt、policy.onnx、manifest.json、hardware_template.json、hashes.json，tracking 还复制 motion.npz。用 32 组真实仿真观测比较 JIT 输出，最大误差和容差检查通过才继续；ONNX 当前只做结构检查，没有宣称 ONNX Runtime 已数值验收。

deploy-sim 只加载导出的 JIT，在同一个 mjlab 后端闭环运行；它不是独立第二物理引擎，也不是上真机证明。硬件模板默认禁用，无通信网卡/域和发送指令实现，保留 PD/关节映射/控制周期以及待集成的估计、限幅、状态机、看门狗与急停接口。

## 17. 结果文件与故障定位

正式训练在 outputs/runs，性能测试在 outputs/benchmarks，评估在 outputs/evaluations，导出在 outputs/deploy。动作原始/转换数据在 motions/raw 和 motions/processed。源码更新的旧文件在 .cache/update-backups，更新不会删除这些结果。

遇到异常先保留完整 traceback、运行目录和具体模型路径。单看 kernel load/cached 日志不是报错；“进程正常结束”也不是行走质量验收。安装/代码错误看 traceback，训练质量看同协议评估和回放，资源不足看资源 JSON 和 nvidia-smi。
